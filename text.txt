# 八、优先检查的几个方向

不要默认某一方向一定是原因，必须通过证据确认。

重点检查：

## 1. Task 是否过大

检查 PROJ-001 是否试图一次完成：

```text
大量代码分析
+
架构理解
+
大量修改
+
测试
+
最终验证
```

如果是，判断是否需要拆成一个更小但仍然真实的工程任务。

例如：

```text
单文件修改
+
单一行为变化
+
针对性测试
```

注意：

> 不能把任务缩小到没有实际工程价值的 toy task。

---

## 2. Timeout 配置

检查：

```text
timeout
deadline
retry
polling
process lifetime
subprocess handling
idle timeout
hard timeout
```

判断 timeout 是：

```text
REAL_FAILURE
```

还是：

```text
ORCHESTRATION_TIMEOUT
```

即 Agent 实际还在正常执行，只是 Agent OS 提前杀掉。

不得为了让实验“成功”而无条件把 timeout 调得极大。

必须说明：

```text
CURRENT_TIMEOUT:
WHY_INSUFFICIENT:
NEW_TIMEOUT:
WHY_JUSTIFIED:
```

---

## 3. Agent 是否陷入无效循环

检查：

```text
重复读取文件
重复搜索
重复修改
重复测试
等待命令
等待用户
```

寻找：

```text
LOOP
STALL
IDLE
RETRY_STORM
```

如果发现，优先采用最小的执行控制修复。

---

## 4. Project Environment

检查：

```text
JDK
Maven / Gradle
dependencies
working directory
git state
build configuration
test configuration
environment variables
```

确认 Agent 是否实际上被环境问题阻塞。

---

## 5. Task → Runtime 参数传递

检查：

```text
task
→ loop controller
→ runtime adapter
→ host
```

确认：

```text
working directory
task prompt
timeout
environment
runtime selection
```

没有在链路中丢失或错误覆盖。
