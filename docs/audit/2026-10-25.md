## P0

### P0-1 迁移不是单事务：`executescript()` 提前提交，失败后 schema 与版本号不一致 —— fixed in `f39cf6d`

**位置**

- `aos/core/memory/migrations.py:206-222`（外层 `BEGIN IMMEDIATE` / `commit` / `rollback`）
- `aos/core/memory/migrations.py:408-423`（v2 的 `executescript`）
- `aos/core/memory/migrations.py:434-453`、`465-472`、`514-527`（v3/v4/v5 的 DDL 全部在 `executescript` 内）
- `aos/core/memory/migrations.py:160-164`（docstring 声称"one transaction each"）
- `aos/core/memory/migrations.py:257-259`、`230-244`（baseline 同样用 `executescript`，且只检查 `memories` 表）

**证据**

```python
# migrations.py:206
conn.execute("BEGIN IMMEDIATE")
try:
    migration.apply(conn)          # v2/v3/v4/v5 内部调用 conn.executescript(...)
    conn.execute(f"PRAGMA user_version = {migration.version}")
    conn.execute("INSERT INTO schema_meta ...")
    conn.commit()
except Exception as exc:
    conn.rollback()
```

```python
# migrations.py:411
conn.executescript(
    """
    CREATE INDEX IF NOT EXISTS idx_memories_type ON memories(type);
    ...
    """
)
```

```python
# migrations.py:160
"""Run every pending migration, one transaction each.

``dry_run`` answers "what would change" without writing ...
Each migration commits or rolls back alone, so a failure at v5 leaves v4 intact ...
"""
```

**影响**

- Python `sqlite3` 的 `executescript()` 在执行脚本前会**隐式 COMMIT** 当前事务。因此 `BEGIN IMMEDIATE` 对 v2–v5 实际上没有覆盖 DDL；脚本中途失败时，已执行的 `ALTER TABLE` / `CREATE INDEX` 已经落盘，`conn.rollback()` 无法撤回。
- v3 是最直观的永久故障：若 `ALTER TABLE observations ADD COLUMN confidence` 成功、后续语句失败，版本仍是 v2；下次打开再次执行 v3 会报 `duplicate column name: confidence`，数据库无法自动恢复。
- v2 更隐蔽：`_rebuild_table()` 在 `executescript()` 之前完成，`executescript()` 一执行就把重建提交；若在 `PRAGMA user_version = 2` 之前崩溃，文件是 v2 形状但标记 v1，下一次打开被 `_expect_v1_shape()` 拒绝（`aos/core/memory/migrations.py:391-405`），只能手工改 pragma 或恢复备份。
- baseline 也有同类问题：`schema.sql` 中途失败后只要 `memories` 已存在，`_has_baseline()` 就返回真，下一次打开把半成品标成 v1，再走迁移；缺失的 `schema_meta`/`observations` 会以原始 `sqlite3.OperationalError` 暴露。
- 现有测试 `tests/test_migrations.py:189-210` 注入的失败发生在任何 DDL 之前，无法发现该问题；`tests/test_migrations.py:370` 的 docstring 甚至把"DDL 与版本号一起提交"当作既成事实。

**修复方向**（审计后已落地：`f39cf6d` 将迁移改为原子执行、`--dry-run` 改为只读）
- 迁移内不要使用 `executescript()`；把脚本拆成单条 `conn.execute()`，全部放在同一个 `BEGIN IMMEDIATE` 内，版本号与 mirror 的写入也在同一事务。
- baseline 同样改为逐条执行并纳入事务；`_has_baseline()` 应校验 `schema_meta`、`memories`、`observations`、`candidates`、`learning_reviews` 等关键表，而不是只看 `memories`。
- 为每个迁移增加"在第 1 条 DDL 之后抛错"的故障注入测试，断言 `user_version` 与表结构都回到迁移前；再增加"迁移成功后再次打开"的幂等测试。
- 若必须保留 SQL 脚本，使用 `sqlite3.complete_statement()` 自行切分，逐条执行；不要依赖 `executescript()` 的事务语义。

- `aos/core/memory/migrations.py:264-271`（发现 pending 就直接 `migrate`）


```python

    ...

```

**影响**

- 对一个 v1 生产库执行 `aos memory migrate --dry-run`：`MemoryStore()` 先完成 v2 的破坏性表重建和 v3–v5 的全部迁移，然后 `_memory_migrate` 才收到 `dry_run=True`；此时已经无待迁移项，输出 `from=5, to=5, would_apply=[]`，用户看到的是一份"什么都没发生"的报告，但库已经被改写。
- `--to 3` / `--to 1` 同样先被自动升到 v5，再在 `_memory_migrate` 中报 `refusing to downgrade v5 to v3`；`--to` 实际上无法用于"只迁到中间版本"。
- 如果自动迁移在 `MemoryStore()` 内失败，`_memory_migrate` 的 `try/except SchemaError` 根本来不及接管，CLI 直接 traceback；这与"dry-run 是最安全的问法"的 docstring（`aos/core/memory/migrations.py:162-163`）相反。
- 该问题与 P0-1 叠加：dry-run 触发的自动迁移一旦在 `executescript()` 中途失败，会留下 P0-1 的部分迁移库。

**修复方向**
- 在 `cmd_memory` 分派前特判 `memory migrate`：不要构造 `MemoryStore()`；用 `sqlite3.connect()` 打开原始连接，dry-run 以只读方式读取 `PRAGMA user_version` 和表结构，不调用 `ensure_schema`。
- 给 `MemoryStore` 增加 `auto_migrate=False` 或 `open_for_migration()` 入口；迁移命令自己控制事务和备份。
- 增加 CLI 级回归测试：构造真实 v1 形状库，执行 `main(["memory", "migrate", "--dry-run"])`，断言 `user_version` 不变、无 `.bak`、输出包含 `would_apply`；再测 `--to 3` 只迁到 v3。

### P1-4 `loop_id` 被直接拼进路径：postflight 可读写 loops 目录之外的 `.json`

**位置**

- `aos/core/loop/state.py:187-204`（`state_path()` 和 `load()` 都用 `loops_dir / f"{loop_id}.json"`）
- `aos/contract/schema.py:245-251`（postflight 的 `loop_id` 只要求非空字符串）
- `aos/core/loop/lifecycle.py:281`（`LoopState.load(loop_id)`）
- `aos/core/loop/lifecycle.py:402-403`（`state.postflight = doc; state.save()`）

**证据**

```python
# state.py:199
@classmethod
def load(cls, loop_id: str) -> Optional["LoopState"]:
    path = get_paths().loops_dir / f"{loop_id}.json"
    if not path.is_file():
        return None
    return cls.from_dict(json.loads(path.read_text(encoding="utf-8")))
```

```python
# state.py:187
def state_path(self) -> Path:
    return get_paths().loops_dir / f"{self.loop_id}.json"
```

```python
# schema.py:245
for key in REQUEST_REQUIRED[phase]:
    value = payload.get(key)
    require(
        isinstance(value, str) and bool(value.strip()),
        f"{key} is required and must be a non-empty string",
        errors,
    )
```

**影响**

- `loop_id="/etc/passwd"` 会读取 `/etc/passwd.json`；`loop_id="../../tmp/evil"` 会读取 `store/loops/../../tmp/evil.json`。只要目标是一个带 `loop_id/task_id/...` 字段的 JSON，`from_dict()` 就会把它当成合法 loop state。
- 更严重的是写：`from_dict()` 使用文件里的 `loop_id` 字段，`state.save()` 又用它拼 `state_path()`；攻击者可以先在任意可写位置放一个 JSON，把其中的 `loop_id` 设为绝对路径或 `../`，postflight 就会把状态写到 loops 目录之外（固定追加 `.json` 后缀）。
- 宿主是信任边界，但契约目前只校验"非空"，这意味着一个有 bug 的宿主、一个手工构造的 `--payload-stdin`、或未来新增的集成都能越界；审计要求把"宿主可信"当成需要显式声明的假设，而不是路径安全的替代品。

**修复方向**
- 对 `loop_id` 使用白名单正则（例如 `^LOOP-[A-Z0-9-]+$`）或至少 `Path(loop_id).name == loop_id`，并校验 `resolve().parent == loops_dir`。
- `LoopState.load()` 不要信任文件内的 `loop_id` 与请求参数一致；加载后强制 `state.loop_id = loop_id`，或校验二者相等。

### P2-4 `pending.record()` 非原子、清洗会碰撞、超长 session ID 可让 preflight 直接抛 `ENAMETOOLONG`

**位置**

- `aos/core/loop/pending.py:28-39`（`_safe` 过滤字符，非一一映射）
- `aos/core/loop/pending.py:42-73`（`path.write_text` 直接覆盖）
- `aos/core/loop/lifecycle.py:220-242`（`pending.record` 在 `_run_preflight` 的 try 之外）

**证据**

```python

cleaned = "".join(ch for ch in str(session_id or "") if ch.isalnum() or ch in "-_")
return cleaned or "unknown"
```

```python

```

**影响**

- `_safe("a/b")` 和 `_safe("ab")` 都得到 `ab`，两个不同 session 会写同一个 `pending-ab.json`；一个 session 的 postflight `pending.clear()` 会删掉另一个 session 的记录，导致后者的 loop 永远显示为"开着没回来"。
- 超长 session id（尤其是中文，UTF-8 每字符 3 字节）会让文件名超过 255 字节，`write_text` 抛 `OSError: [Errno 36] File name too long`。该调用在 `preflight()` 的 try 之外（`aos/core/loop/lifecycle.py:225`），所以不会返回 fallback，而是直接 traceback 到宿主。

- 磁盘满/权限错误同样会让 preflight 失败；而 pending 只是"记一笔待办"，不应该阻断主流程。

**修复方向**
- 文件名使用 session id 的哈希（或 URL-safe base64），保证一一映射且长度固定；原始 session 保留在 JSON 内。
- 使用 `tempfile` + `os.replace` 原子写入；失败时捕获 `OSError` 并 warning，不阻断 preflight。
- 把 `pending.record()` 放进 `preflight()` 的 try/except，返回 `fallback` 或至少附带 `warnings`。
- 增加测试：`a/b` 与 `ab` 不碰撞、300 字符中文 session 不崩溃、写入中途失败不留下可被误读的半文件。

- `aos/core/loop/lifecycle.py:502-514`（`run()` 直接调用 `_run_postflight`）
- `aos/core/loop/lifecycle.py:433-457`（`postflight()` 有 `try/except` fallback）

- 增加测试：`aos run` 在 `final_status=failed` 时退出码非 0；monkeypatch `_run_postflight` 抛错时仍输出合法 postflight 文档。

**影响**
