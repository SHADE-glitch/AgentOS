## 4. Closed-Loop Gap Analysis

```yaml
component: "Runtime Executor / Pipeline Orchestrator"
exists: false
status: MISSING
impact: "No component calls retrieval_optimizer before task execution"

  There is no executor.py or pipeline.py that:
  1. Receives a task
  2. Calls retrieval_optimizer.py to get Top-K memories
  3. Passes results to the actual agent runtime
  4. Records execution traces
```

```yaml

evidence:
  - "traces contain manually crafted memory_retrieval sections"
  - "retrieval_optimizer.py is standalone CLI, never called by trace generator"
  - "No code path exists from retrieval_optimizer.py → trace generation"
```

### Gap 3: No Sequential Pipeline

```yaml
component: "Sequential orchestrator"
status: DECLARATIVE_ONLY
impact: "Each component runs independently; no automated flow"
evidence:
  - "No Python import between collector/validator/promoter"
  - "No shell script that chains them"
  - "No Makefile or pipeline config"
  - "Each component must be manually invoked in order"
```

### Gap 4: Collector ↔ Trace Connection is Manual

```yaml
component: "Collector trace ingestion"
status: PARTIAL
impact: "Collector reads traces but traces are not auto-generated by the pipeline"
detail:
  - "collector.py has a hardcoded TARGET_EXECUTIONS list"
  - "New traces must be manually added to this list"
  - "No watcher or event-driven trigger"
```

### Gap 5: No Decision-Support Integration

```yaml

status: DECLARATIVE_ONLY

  - "decision-support-protocol.md is a markdown document, not executable"
  - "retrieval_optimizer.py does not reference decision-support-protocol.md"
  - "No code path from retrieval output → router decision"
```

### Gap 6: Retrieval Optimizer → Router is Broken

```yaml
component: "Retrieval Optimizer → Router"
```

## 7. Critical Breakpoints

### Breakpoint 1: Retrieval → Runtime

```text
retrieval_optimizer.py → ??? → actual task execution
                 ^
                 |
           NO CODE PATH
```

This is the most critical gap. The retrieval optimizer produces rankings, but there is **no mechanism** to pass those rankings to the actual agent runtime. The `memory_retrieval` sections in trace files were written by hand during Phase 5.6, not generated by the optimizer.

### Breakpoint 2: Runtime → Feedback

```text
trace → collector.py → memory-candidates.yaml
           ^
           |
    collector has hardcoded trace list
    new traces are NOT auto-discovered
```

### Breakpoint 3: No Pipeline Orchestrator

```text
collector → validator → promoter → reconciler → optimizer → decay
   ^         ^           ^           ^            ^          ^
   |         |           |           |            |          |
   -------- all manual, no sequential execution -------
```

## 11. Recommendations for Phase 5.8.2 Steps 2-12

Given the audit findings, the remaining steps (2-12) require a **runtime adapter** that bridges:

```text
retrieval_optimizer.py → adapter → router/agent → trace → collector → feedback
```

Without this adapter, the closed loop cannot be demonstrated with real execution. The options are:

1. **Build a minimal adapter**: A Python script that takes a task, calls retrieval_optimizer, calls OpenCode CLI, collects traces, and feeds back to collector.

2. **Simulate the loop**: Use existing traces with the retrieval optimizer's output injected, then validate the feedback loop manually.

3. **Accept PROVISIONAL status**: Document that the loop is architecturally sound but awaits a runtime adapter for end-to-end proof.
